# ADR-020: 正規化された内部データと非正規化された互換層を併用する

## 背景

my-searchはJSONベースのカード記録からSQLiteの関係データへ移行しました。正規化された `card_tags` と `card_links` は、検索性、外部キーによる削除、バックリンク、整合性検証を提供します。一方、既存APIの利用者と古いデータ経路は `tags` と `links` の配列を期待しており、カードには互換性や検索経路のためのJSON列とトークン列も残っています。

## 決定

形式を用途ごとに分けて、意図的に併用します。

- 正規化された関係テーブルを、タグとリンクの読み書き、絞り込み、削除時の整合性、検証における正本とします。
- 非正規化されたJSON列とAPI配列は、既存クライアントと移行経路のための互換表現として残します。
- 事前計算トークンと全文検索データは派生した検索表現であり、別の正本にはしません。
- 書き込みは正規化された表現を先に更新し、現在のリポジトリ契約が求める範囲で互換データも同期します。

これは意図的な併用です。内部DBの正しさと検索性を守りながら、既存API利用者に破壊的変更を強制しないためです。

## 代替案

- JSON配列だけを残す: 関係検索、バックリンク、削除時の整合性、検証が弱くなり、処理コストも増えるため採用しない。
- 互換フィールドを直ちにすべて削除する: 既存API利用者を壊し、移行を不必要に大きくするため採用しない。
- 両方の表現を独立した正本として扱う: 乖離した場合に返却値とDB関係の意味が不明確になるため採用しない。

## 結果

- DBは明示的な関係制約と効率的な関係検索を持ちます。
- 既存クライアントは従来どおり配列形式のAPIフィールドを受け取れます。
- 2つの表現が共存するため、同期と移行のテストが必要です。
- 互換フィールドが残っていることを、正規化テーブルが正本でない根拠にしてはいけません。
- 互換層の削除は、後の破壊的変更として判断する事項であり、偶発的な整理ではありません。

## コード上の根拠

- `repositories/cards_repository.ts`
- `repositories/card_tags_repository.ts`
- `repositories/card_links_repository.ts`
- `db/migrate.ts`
- `docs/project-details.md`

## 見直し条件

対応するすべてのAPI利用者が関係データを扱えるレスポンスへ移行し、公開契約を壊さずにバージョン付きAPIから互換フィールドを削除できる段階で見直します。
