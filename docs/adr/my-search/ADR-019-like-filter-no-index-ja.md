# ADR-019: カード一覧のフィルタ(`q=`)は索引でなくLIKEを使う

## 背景

`GET /api/cards?q=`は`title LIKE '%...%'`で絞り込んでいます。`EXPLAIN QUERY PLAN`で確認すると`SCAN cards`と表示され、`idx_cards_title`は使われていません。B-tree索引は共通の前方一致部分を持つ値へはジャンプできますが、「どこかにこの文字列を含む値」へジャンプする手段は持たないため、先頭にワイルドカードがあるLIKEは行数によらず索引の対象外になります。

## 決定

LIKEによる部分一致フィルタはそのまま維持します。現在のデータ(233行、同一ファイルの複製2つに対して同一条件・ウォームアップ込みで計測)で条件を揃えて実測したところ、索引を使う完全一致は1クエリあたり約7.1マイクロ秒、索引なしの同等なフルスキャンは約43.5マイクロ秒で、約6倍の差がありました。ただしこの高速化は前方一致・完全一致に限られ、任意の部分一致検索には行数によらず適用できません。これは見落としではなく、記録されていなかった既存のアーキテクチャ境界の明文化です。`cards_fts`(ADR-018参照)は既にFTS5ベースの全文検索の代替手段として存在しており、部分一致検索の速度が問題になった場合の自然な移行先です。

## 結果

- `q=`のフィルタコストは索引参照ではなく、走査した行数に比例します。
- 挙動の変更はありません。既存の、これまで文書化されていなかったアーキテクチャ境界を記録するものです。
- 部分一致検索の速度が将来ボトルネックとして実測された場合、対処は先頭ワイルドカード付きLIKEを索引化しようとすることではなく、`cards_fts`経由にルーティングすることです。

関連: [ADR-018: 転置インデックスが存在しないことの記録](ADR-018-no-inverted-index-ja.md)

## 撤回条件

より大きいコーパス規模での本番相当のプロファイリングで、`q=`のスキャンが測定上のボトルネックになったことが確認された場合に再検討します。
