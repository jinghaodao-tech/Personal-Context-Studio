# ADR-005: SQLiteによるローカルファースト保存

## 背景

このポートフォリオアプリは単一ユーザー・ローカル利用のツールです。

## 決定

標準の永続化先はローカルSQLiteとする。バージョン管理されたマイグレーションと、ローカルファイルシステムへのバックアップ/復元スクリプトを使う。

## 代替案

PostgreSQL、Elasticsearch、ホスト型の同期サービス、ベクトルDB。

## 結果

ネットワークなしで利用でき、クラウドの認証情報が無くても動作する。

## 見積もり: この規模でのSQLiteとElasticsearchの比較

現在のデータで実測: `data/cards.db`は`cards`233行(`card_tags`・`card_links`・FTS5索引`cards_fts`を同一ファイルに含む)で2,228,224バイト、1行あたり約9.6KBです。`docs/benchmark.md`で既に使っているベンチマーク規模(10,000行)まで線形に外挿すると約96MB、100,000行で約960MB程度になります。SQLiteは別プロセスを持たず、OSのファイルキャッシュ以外に固定のメモリ消費が無く、単一ファイルとしてバックアップできます(`scripts/backup.ts`)。

Elasticsearchの固定コストはデータ量に依存しません。別プロセスとしてJVMを起動する必要があり、小規模な単一ノード構成でも一般的に推奨される最小ヒープはおおよそ1〜2GBです。加えて内部の索引構造により、ディスク使用量は元データのおおよそ10〜30%増しになるのが一般的な運用上の目安です(このデータセットで実測したものではありません)。上記の規模(数百〜数十万行程度)では、このJVMの固定コストだけでSQLiteのファイル全体を1〜2桁上回り、単一ユーザーのこのアプリには不要なクラスタ・ノード管理のオーバーヘッドは含めていません。

この規模での判断を分けているのは生のクエリ速度ではなく固定オーバーヘッドの差であり、Elasticsearchの優位性が効いてくるのは、このアプリが到達を想定していないデータ量・クエリ量の領域からです。

## コード上の根拠

`db/database.ts`、`db/migrate.ts`、`scripts/backup.ts`。

## 撤回条件

明確に承認されたマルチユーザー展開が必要になった場合、またはコーパス規模がSQLite自身の実測された伸び方(`docs/adr/ADR-018-no-inverted-index-ja.md`参照)で無視できなくなる領域に近づいた場合に再検討する。
