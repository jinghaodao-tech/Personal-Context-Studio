# ADR-015: 高頻度フィールドのオプトイン自動確定と、生理情報・個人情報カテゴリに対する追加同意

## Status

実装済み。何が実装され、後続のマイグレーションで何を修正し、まだ挙動テストが無い部分は何かは下記「Implementation」を参照。

## Context

ADR-002は、AIや連携先が生成した値が分析・共有の対象になる前に、フィールド単位で人間が判断することを要求している。これは既定として今も正しい——人間が一度も見ていない値が分析対象になってはいけない。

実際の日常利用で、この既定がうまく機能しないケースが見つかった(`docs/usability-findings.md`「Design tensions observed in real use」)。高頻度・低リスクな習慣——短い毎日のチェックイン——が、監視対象フォルダに直接Markdownを書き込む形で記録されていた(PCSはエディタ非依存なので、AIアシスタントを単なるテキストエディタとして使うことも含め、どのエディタでもこれは可能)。ADR-002が要求するフィールド単位のReview/確定は、これらの記録では一度も行われていなかった。記録の習慣自体は続いていたが、データは確定されず、確定済みの値しか受け取らないMeTheory(Markdown本文は一切受け取らない)には何一つ届いていなかった。1件ごとの確定UIには固定コストがあり、毎日の習慣的な記録には見合わない。

候補となる解決策は、Templateで特定のフィールドに`autoConfirmOnIngestion: true`を設定できるようにし、対象を申告済み`sensitivity: normal`のフィールドに限定することである。しかしこれは単独の関門としては安全ではない。`sensitivity`自体が、そのフィールドについて人間が意図的に設定した値とは限らないからである。

- `apps/api/src/routes/templates.ts:136`は、外部連携がテンプレートフィールドのリクエストを送信する際に`sensitivity`を省略すると、黙って`"normal"`をデフォルト値とする。
- AI支援のテンプレート下書き生成機能(`packages/ai-core/src/index.ts`)は、フィールドのテーマ・ラベルから`sensitivity`をフィールドごとに推論し、3つの正当な値のいずれかであればそのまま返す。AI下書きに対する人間のレビュー手段は、警告付きの生JSONテキストエリア(「AIの案は確定値ではありません。内容を確認・修正してから保存してください」)だが、フィールドごとのレビューを強制する仕組みはなく、人間はAIの誤った推測を修正せずに保存できてしまう。

したがって、`sensitivity: normal`だけを根拠に自動確定を許可すると、"normal"というラベル自体が人間によって一度もレビューされていないフィールドを自動確定してしまうリスクがある。

一方で、このプロダクトのドメインモデルの中核をなすフィールド——睡眠時間・睡眠の質・疲労・エネルギー・気分・回復(姉妹リポジトリMeTheoryの`packages/self-understanding`が既にモデル化しているのと同じカテゴリ)——は、まさに生理情報や個人情報カテゴリに該当しやすいフィールドであり、同時に低摩擦化の目的が本来助けたかったフィールドでもある。これらのカテゴリを一律に恒久ブロックすると、そもそも実使用の発見が示した摩擦の問題を再生産するだけになる。

## Decision

既存の`isSecretLike`パターン(`packages/domain/src/index.ts`。申告されたsensitivityに関わらず、ルールベースであえて過剰検出気味に設計された検出器が値をブロックできる仕組み)にならい、独立した・互いに代替不可能な2つの関門を設ける。

1. Templateのフィールドに`autoConfirmOnIngestion: true`を設定できるのは、申告済みの`sensitivity`が`normal`の場合のみとする。
2. 申告されたsensitivityとは独立に、すべてのフィールドをルールベースの生理情報・個人情報検出器にかける。ここでいう生理情報とは: 睡眠(時間・質)、疲労・エネルギー・体調全般、心拍、血圧、体温、体重その他の生体計測値、月経周期・生殖に関する情報、症状、服薬・通院記録、身体症状の主観的な報告(頭痛・動悸など)を指す。気分・精神状態系のフィールドも、身体症状の報告と単なる感想をキーワードマッチングだけで確実に区別することはできないため、過剰検出側に倒してこの検出器の対象に含める。個人情報とは、氏名・連絡先・住所などの直接的な識別情報を指す。この検出器の役割はフィールドを問答無用でブロックすることではなく、そのフィールドに対して自動確定を有効化する際に追加の同意が必要かどうかを決めることである。
3. 検出器に該当するフィールドについては、`autoConfirmOnIngestion`を有効化する際に、通常のテンプレート保存操作とは別の、明示的な確認ステップを要求する。このフィールドが生理情報または個人情報に分類されていること、自動確定を有効にすると以降の値が個別のレビューなしで確定されることを明示した専用ダイアログを表示する。この同意は1エントリごとではなく1フィールドごとに一度だけ行えばよいが、フィールドの申告sensitivityまたは検出器の判定が変化した場合は再度表示する。
4. 検出器に該当しないフィールドについては、`autoConfirmOnIngestion`の有効化は通常のテンプレート編集フローのまま、追加のステップなしで行える。
5. この経路で確定された値は、`user_confirmed`とは別のprovenance(`auto_confirmed_low_sensitivity`)を持つ。これはADR-013が`machine_measured`を`user_confirmed`と区別して保持しているのと同じパターンである。自動確定された値は、履歴上いつでも個別レビュー済みの値と区別できなければならない。
6. sensitivityの申告、生理情報・個人情報検出器、追加の同意ステップは、それぞれ独立しており、該当する場合はすべて必須である。どれか一つだけでは十分ではない。この冗長性は意図的なものであり、どこか一箇所の誤った推測(例:レビューされていないAI下書きのsensitivity値)だけでは、レビューされず異議も唱えられない確定値が生まれないようにするためである。

本ADRはADR-002の既定を変更しない。あるフィールドに対して明示的に`autoConfirmOnIngestion`を有効化しない限り、そのフィールドのすべてのエントリは従来どおり1件ごとのReviewを要求される。

## Alternatives

- **申告済み`sensitivity: normal`だけを根拠にする:** 却下。sensitivityはレビューされていないAI推測や、省略時の黙示的デフォルトである可能性があり、これだけでは特定のフィールドが自動確定して安全かどうかを人間が判断した保証にならない。
- **生理情報・個人情報検出器に該当するフィールドの自動確定を恒久的にブロックする:** 却下。これは低摩擦化の目的が本来助けたかったフィールド(睡眠・気分・疲労・エネルギー)を恒久的に除外してしまい、`docs/usability-findings.md`が記録した摩擦の問題を解決するどころか再生産する。
- **既存のAI下書きレビューUI(警告付きの生JSONテキストエリア)を十分な人間レビューとみなす:** 却下。このフローには保存前のフィールド単位レビューを強制する仕組みが何もなく、AIのsensitivity推測が未検証のまま通過しうる。この欠陥こそが本ADRの直接の動機である。

## Consequences

- 個人情報・生理情報に明確に該当しないフィールド(プロジェクトやタスクのメタデータなど)は、Templateレベルで一度オプトインすれば、追加の儀式なしに低摩擦の自動確定を得られる。
- 検出器に該当するフィールドは、`autoConfirmOnIngestion`を有効化する前に一度だけ、意図的な追加の確認を要求される——ただし1エントリごとではなく1フィールドごとに一度なので、これらのフィールドを含む毎日の記録習慣も、その1ステップの後は低摩擦になりうる。
- 自動確定された値は、監査・履歴上、常に個別レビュー済みの値と区別可能なまま保たれる。
- 検出器は、偽陰性(本当に生理情報・個人情報に該当するフィールドを見逃し、未検証のまま低摩擦自動確定に紛れ込ませてしまうこと)よりも、偽陽性(追加の同意が不要だったフィールドにフラグを立て、確認ステップが1回余計に発生すること)を許容する方向にチューニングすべきである。これは本プロジェクトの他のADRで既に採用されている非対称リスクの原則と同じである(MeTheory ADR-014「失敗の方向は非対称」を参照)。
- 実装作業——検出器の具体的なパターンリスト、同意ダイアログ、新しいprovenance値、そのマイグレーション——は本ADRの範囲外であり、本ADRによって許可されるものではない。

## Implementation

コミット`2c09fce feat(pcs): implement opt-in auto-confirm consent`で実装された。`apps/api/src/autoConfirm.ts`(検出器`autoConfirmClassification`、3分岐の関門`autoConfirmAllowed`)、マイグレーション`023_opt_in_auto_confirm_elevated_consent`(`context_template_fields`に`auto_confirm_on_ingestion`・`auto_confirm_consent_granted_at`・`auto_confirm_detector_version`・`auto_confirm_detector_flagged`を追加)、新しい`POST /v1/context-templates/:id/fields/:fieldKey/auto-confirm`エンドポイント(`apps/api/src/routes/templates.ts`)、そして候補作成時(`apps/api/src/routes/entries.ts`)の取り込み時チェック——フィールドが有効化されており、`sensitivity === "normal"`で、保存済みの検出器スナップショットが最新(`detectorFresh`)であり、フラグが立っている場合は同意済みであることの全てを満たした場合のみ`auto_confirmed_low_sensitivity`として確定する。Decision3の「フィールドの申告sensitivityまたは検出器の判定が変化した場合は再度表示する」という要件は、1つではなく2つの独立した仕組みで満たされている:sensitivityがnormalから変わった場合は取り込み時に常に自動確定そのものをブロックし(関門1)、検出器の判定が変わった場合(例:同意後にラベル・説明文が編集された)は`detectorFresh`の鮮度チェックで捕捉し、ダイアログを自動的に再表示するのではなく手動レビューにフォールバックする。

このコミット自身が追加したテスト(`test/migrations.test.ts`)は、マイグレーションが適用され新しいカラムが存在することだけを確認しており、`autoConfirmClassification`や`autoConfirmAllowed`自体の挙動、新エンドポイントや取り込み経路そのものは一切テストされていなかった。この挙動テストを追加する過程で、以下の2点を発見・修正した。

- **単なる不足ではなく実際のバグ**: `apps/api/src/routes/templates.ts`の成功パスは`provenance({ subjectType: "template_field", ... })`を呼ぶが、`context_provenance.subject_type`のCHECK制約はもともと`"template_field"`を許可していなかった。そのため新エンドポイントへの成功呼び出し(有効化・無効化のどちらも)は毎回CHECK制約違反で`500`を返しており、フラグの有無に関わらずこの機能はどのフィールドに対しても一度も有効化できない状態だった。マイグレーション`024_provenance_template_field_subject`(`022_remeasurement_revision_type`が自身のCHECK制約変更で使ったのと同じ、rename→recreate→copy→dropのパターン)と、対応する`db/schema.sql`の更新で修正した。
- **追加したテストカバレッジ**: `test/auto-confirm.test.ts`(ユニットレベル。`autoConfirmClassification`の正規表現検出器を英語・日本語の生理情報/個人情報用語で確認し、`autoConfirmAllowed`の3分岐すべてを確認)と`test/auto-confirm-flow.test.ts`(HTTPレベル。sensitivity関門、同意不要パス、追加同意必須パス、取り込み時に有効化された両フィールドがprovenanceイベント付きで自動確定されレビュー待ちキューから除外されること、`detectorFresh`の鮮度チェックが手動レビューへフォールバックすることを確認)。

未カバー: 追加同意ダイアログ自体はクライアント側UIの話であり、ここで参照した実装には含まれていない。そのため「フィールドの申告sensitivityまたは検出器の判定が変化した場合は再度表示する」はAPI層でのみ検証されており(上記参照)、Decision3が述べるUI層では未検証。

## Reversal

検出器の偽陰性率が実運用上高すぎると判明した場合(生理情報・個人情報に該当するフィールドが、追加の同意ステップを一度も通らずに自動確定されてしまった場合)、あるいは追加の同意ダイアログ自体が、現在のAI下書き警告と同様に読まれずにクリックされて通過するだけのものになってしまった場合は、見直しが必要である。そのいずれの場合も、検出器のキーワードリストを調整するだけでなく、この二段階の仕組みそのものを再検討する必要がある。
