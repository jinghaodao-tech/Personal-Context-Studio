# ADR-021: review-classificationsの未使用reasonsを廃止し、sensitivity検出器のLLM化計画を非LLM構成に置き換える

## ステータス

実装済み（決定論的3層検出器とreasons廃止）。

## 背景

**1. `POST /v1/experience/review-classifications`の`reasons`要件に、実際の呼び出し元が存在しない。** `high_confidence`判定には`confidence>=0.9`・`sensitivity==="normal"`・競合なしに加えて、空でない`reasons`配列(フォーマットのみ正規表現で検証、中身は未検証)を要求しているが、アプリ全体をgrepしても呼び出し元は`test/experience.test.ts`だけ。MCPツールにもダッシュボードにもCLIにも存在しない。「理由を言語化させる」という意図自体、人間が書くならAuto化の意味が薄れ、AIが書くならその理由の妥当性を誰も検証しない、という指摘の通り。

**2. auto-confirm検出器(ADR-015、`autoConfirm.ts`)は、`physiological-personal-v1`という1本の正規表現で、フィールドの`key`/`label`/`description`だけを見ていて、実際の値は見ていない。** 既存テスト(`test/auto-confirm.test.ts`)は自分のキーワードリストに自分がマッチすることを確認してるだけの循環テストで、「怒り」「収入」「性的指向」のような未収録語での検証がなく、実測の精度は存在しない。これを`packages/ai-core`の既存ローカルLLM(デフォルト`llama3.2`、Ollama経由)に置き換える案は検討の上で却下した: 3Bクラスの汎用チャットモデルはこの用途の判断力として心もとなく、日本語も英語ほど強くない。しかもこの検出器はまさに「AIの自己申告を信用しない」という、このプロジェクトが他の箇所(ADR-015やADR-020のprovenance設計)で徹底してきた原則の急所にあたる。より強いローカルモデル(Swallow 70Bクラスなど)は精度は上がりそうだが、個人のPCで常時稼働させるにはGPUが要り、ローカルファーストで無料というこの製品の前提と衝突する。

## 決定

**1. `reasons`要件と関連カラムを`review-classifications`から削除する。** `confidence>=0.9`・`sensitivity==="normal"`・競合なしの3条件は維持。誰も読まない・誰も呼ばないフィールドを「将来のため」残さず、廃止する。

**2. sensitivity/auto-confirm検出パスにLLMを追加しない。** 代わりに`autoConfirm.ts`の正規表現1本を、非生成AIの3層構成に発展させる。

- **キーワード層(既存の正規表現を置き換え)**: 個人情報保護法第2条3項の「要配慮個人情報」11類型(人種・信条・社会的身分・病歴・犯罪の経歴・犯罪被害の事実・心身の障害・健康診断等の結果・その結果に基づく指導・刑事手続・少年保護手続)を土台にし、法定リストではカバーされない本プロジェクト独自の対象(気分、収入、性的指向など)を明示的に追加する。法的根拠のあるリストにしつつ、それが上限ではなく土台であることを明記する。
- **意味的類似度層(新規)**: 日本語Sentence-BERT系モデルでフィールドのkey/label/descriptionを埋め込み、キーワード層の各カテゴリから作った例文集とのコサイン類似度で判定。「怒りの強さ」のようにキーワードそのものは含まないが意味的に近い表現を拾える。
- **値内容PII層(新規、対象範囲が異なる)**: `pii-ja-ner-onnx`(Apache-2.0、日本語BERTベースNER、ONNX/INT8量子化、約105MB、Hugging Face `ssl-jp/pii-ja-ner-onnx`)で、実際に記録された値そのもの(フィールドのメタデータではなく)から氏名・住所・電話番号等の明示的な識別子を検出する。フィールド単位の他2層では原理的に見えない範囲をカバーする。

3層はORで結合する。ADR-015が既に確立した非対称リスクの原則(どれか1層が「怪しい」と言えば、他の層が「安全」と言っても上書きされない)をそのまま踏襲する。これはADR-015の3ゲート構造(宣言されたsensitivity・検出器・elevated consent)を置き換えるものではなく、その「検出器」部分の内部実装を作り直す提案。

## 実装

- `autoConfirm.ts`を`non-llm-layered-v2`へ更新し、法令由来・製品拡張キーワード、
  決定論的な類似語、値のPIIパターンをORで組み合わせた。取り込み時には実値も検出器へ渡す。
- migration `027_retire_review_classification_reasons`で`reason_json`を削除し、
  `review-classifications`はreasonsを要求・保存・表示しない。高信頼判定の3条件は維持する。
- adversarialな項目名、値PII、誤検出候補、migration冪等性をテストした。LLM・外部サービスは使用しない。

## 検討した代替案

- **既存ローカルLLM(現行モデル)を使う**: 却下。3Bクラスの判断力は今のキーワードのみの検出器と大差なく、レイテンシ(数百ms〜数秒)とテストの非決定性が増えるだけ。
- **より強いローカルLLM(Swallow 70Bクラス等)を使う**: 却下。精度は上がりそうだが個人PCでの常時稼働にGPUが要り、推論も数秒〜数十秒かかるため、ingestion/auto-confirm時に同期的に走らせる用途に合わない。
- **PII層にMicrosoft Presidioを使う**: 却下。PresidioはPython製、PCSはNode/TypeScript一貫構成。導入すると別ランタイムのプロセスをsupervisorの管理対象に増やす必要があるが、`pii-ja-ner-onnx`はONNX形式なので`onnxruntime-node`でNodeプロセス内に直接組み込める。
- **PII層にCloud DLP(Google Cloud DLP/AWS Macie)を使う**: 却下。外部APIにフィールド・値の内容を送信する必要があり、これはADR-016の外部AI同意フローが明示的にゲートしている類の開示そのもの。「何かを外部に出していいか判定する仕組み」自体が無条件に外部送信するのは矛盾。
- **reasonsを将来のために残す**: 却下。テストコード以外に書き手がいないフィールドは「将来の拡張余地」ではなく、確認するまで存在に気づかれない穴でしかない。本当に理由を記録する仕組みが要るなら、実際の呼び出し元と実際の検証ロジックが揃ってから作る。

## 根拠と影響

このADRの時点では何も実装されていない。決定したのは方向性(このパスにLLMを使わない・非LLM3層構成にする・reasonsを削除する)であり、`pcs_review_classifications`からの`reason_json`/`confidence`削除マイグレーション、`onnxruntime-node`の統合、埋め込みモデルの統合、キーワードリストの正確な中身は、いずれもこのADR単体では未着手・未承認。

3層のどれかを実装する前に、今の循環テストではない、ラベル付き評価データセットが要る: 法定カテゴリ・独自拡張・意図的に紛らわしい表現(「怒り」「収入」「性的指向」のような今回見つかった穴、および「energy」がPCの消費電力を指す場合のような誤検出リスク)を含む実例集合を作り、各層および組み合わせ後の再現率・適合率を実測してから既存検出器を置き換える。設計意図だけで精度を仮定しない。

値内容PII層(`pii-ja-ner-onnx`)は他の2層と対象範囲が異なる(値を見る、フィールドメタデータではない)ため、キーワード/埋め込み層の作り直しを待たずに独立して導入できる。

reasons削除は影響範囲が小さい(現状呼び出し元が存在しない)ため、検出器の作り直しを待たずに先行して着手できる。

## 撤回条件

「LLMを使わない」という決定は、一般的な個人PCで常時稼働できるローカルモデルが、このADRが要求する同じ評価データセット上で非LLM3層構成より有意に高い精度を出せるようになった場合に見直す。これは今この瞬間のコスト・精度・レイテンシのトレードオフについての判断であって、AI活用そのものへの恒久的な反対ではない。
